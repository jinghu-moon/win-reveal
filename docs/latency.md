# 时延基线

`tests/latency.rs` 在**真实弹窗**下测端到端 wall clock：计时点在父进程，包住
`Command::output()` 的整个往返——那是调用者实际等的时间，含进程启动本身。二进制里没有塞任何
计时代码：A/B 两档是"不碰 COM"的地板，C..F 减掉 A 就是 shell 那一段的代价。

复跑：

```powershell
REVEAL_LATENCY_TEST=1 cargo test --test latency -- --ignored --nocapture
```

## 数据

本机（build 26100），两种形态各跑一遍。括号里是 min – max，括号外是 median。零依赖那轮一帧里
有 8–12 个标签要遍历，官方绑定那轮 12–16 个——**探针遍历的标签数就是它的输入**，两轮的差里有
一部分是这个，不是绑定差异：

| 档 | 场景 | 零依赖形态 ms | 官方绑定形态 ms |
|:--|:--|:--|:--|
| A | `--help`：进程启动+退出，不进 COM | 18（17 – 151）n=15 | 18（18 – 156）n=15 |
| B | dry run：再加 `resolve()` 与存在性检查，仍不进 COM | 17（17 – 18）n=15 | 18（17 – 19）n=15 |
| C | 冷：目标目录没在任何标签开过 | 934（892 – 944）n=4 | 957（952 – 989）n=4 |
| D | 暖：目录就是可见标签、条目已在列表里（同一文件第二次 reveal） | 51（49 – 67）n=8 | 59（57 – 76）n=8 |
| E | 暖但条目**刚写入**：先等 Explorer 刷新，再落到 shell | 544（375 – 1194）n=3 | 585（414 – 1070）n=3 |
| F | 后台标签 + 默认 `newtab` 策略 | 1140（1079 – 1268）n=3 | 1280（1106 – 1496）n=3 |

## 与退避改造之前对比

同一段测量代码，把三段固定 200 ms 轮询换成 25 ms 起步、200 ms 封顶的退避，并把
`ensure_selected` 每轮两次全量 `Shell.Windows` 重举合并成一次之后：

| 档 | 改造前（13–17 标签） | 改造后（本轮） | 差 |
|:--|:--|:--|:--|
| D 暖 | 65 / 71 | 51 / 59 | −14 / −12 ms |
| C 冷 | 1187 / 1711 | 934 / 957 | −253 / −754 ms |
| F 后台标签 | 1521 / 1703 | 1140 / 1280 | −381 / −423 ms |
| E 条目刚写入 | 574 / 595 | 544 / 585 | 中位数几乎不动，min 从 565/343 降到 375/414 |

E 不动是有意义的结论：**那一档的等待是 Explorer 自己的列表刷新**，不是我们的轮询粒度。
改造前固定 200 ms 一格时，5 ms 就到账的结果也要等满一格；现在最早的重试间隔是 25 ms，
所以 E 的下界反映了 shell 的真实刷新速度。

## 读法

- **地板 18 ms，dry run 只要 17–18 ms**：参数解析、路径归一与 `exists()` 都不是瓶颈。
- **暖路径 ~50 ms**（D − A）：`CoInitializeEx` + 遍历一帧里 8–16 个标签的 `IDispatch` 迟到绑定
  + `SelectItem` + 置前。"在你正看着的文件夹里换选一个文件"就这么多代价，且随标签数线性增长。
- **秒级全部花在等，不花在调用**：C/E/F 的量级来自三段有上限的等待——
  `select_in_already_open_view` 最多等 2 s、`ensure_selected` 最多等 3 s、
  `Navigate2` 后重新列举最多等 1.5 s，都由 `poll_within`（25→200 ms 退避）驱动。
- **冷档的首个样本最贵**：改造前四个原始取值 2091/1088/1239/1136 ms，第一条多出的约 1 s 是本会话
  第一次激活 `Shell.Application` COM 服务器；本轮 924/892/944/944 ms 已经看不出这个台阶，
  因为同一测试进程里前面的档位已经把服务器激活过了。
- **两种形态同数量级**（D 51 vs 59 ms），与"绑定来源不改变可观察行为"一致；A 档两个 15x ms 的
  最大值是孤立尾延迟（杀软/调度），不是绑定差异。
- **F 仍然比 C 慢**是这台机器上的真实代价：默认策略要把后台标签带出来，除等待之外还有 shell
  多开重复标签的成本。不想付这笔就把策略设成 `overwrite`（不新增标签，代价是替换你正在看
  的那个标签的内容）。
- 跑之前确认没有别的进程在动资源管理器：有一次后台留着被中断的探针，C 档出现了 15 s 的
  尾延迟，清掉之后三遍都不再现。

## 对环境的影响

一次运行新开 4 个夹具标签（C 的四个目录，D/E/F 复用它们；最近两实测 8→12、12→16），结束只关
**整帧都属于夹具**的窗口——与你自己的标签共用一帧的那些不关，一起关会把你的页带走。测试自己会打印
起始与结束标签数，别假设它清理干净了。
